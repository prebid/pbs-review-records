## Beyond the rules

- The change adds `userSync.iframe` with the same URL and user macro as the existing `userSync.redirect` (git a4ab20fef908:static/bidder-info/pixfuture.yaml:17-19). The sync endpoint answers both with a 302 to the setuid URL, keeping the format Prebid Server asks for (`f=b` for iframe, `f=i` for redirect), so the two syncs behave the same; with both declared, cookie_sync now returns the iframe sync wherever iframes are allowed (record local-server pixfuture-a4ab20fef908 v1 cookieSync). Of the 73 bidders at base that declare both, 2 use one URL for both (cwire, inmobi). Not a rule; a reviewer may ask why both are declared.
- The sync server rebuilds the setuid URL rather than redirecting to it as given: it reorders the parameters and adds `us_privacy` (record sync-follow pixfuture-a4ab20fef908 v1 hops[0].location). Prebid Server's setuid does not read `us_privacy`, and the browser loads set the cookie, so it has no effect; it was already so for the redirect sync at base.
- The PR comes from the author's fork's `master`, which still holds the commits of the earlier pixfuture adapter PR; against master the PR changes only these 3 lines (record commit-pair pr-5100 v1).
