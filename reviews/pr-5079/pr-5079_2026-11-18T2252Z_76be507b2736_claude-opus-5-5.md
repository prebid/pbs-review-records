## Beyond the rules

- What the PR changes. encodeValueToBuffer now writes type, key, bidid and bidder as JSON strings through writeJSONString (git 76be507b2736:prebid_cache_client/client.go:183-205, :216-219), so a quote or backslash in them can no longer end the string and add fields or put objects; ttlseconds and timestamp keep their omission when not positive (:185-188, :207-210). PutJson stops reading uuids past the values it sent (:130-133) and, when the response has more entries than values, returns as many empty uuids with the error "more responses than requested" (:147-151), where master, for an extra entry with a string uuid, indexed past uuidsToReturn and panicked (git 4e296450de2f:prebid_cache_client/client.go, processResponse); an extra entry without one was only logged. Tests: TestEncodeValuesStringFields, TestEncodeValuesKeyCannotAddPut, TestEncodeValuesOptionalFields, TestPutJsonResponseEntries (exact, fewer, empty, excess, invalid entries) in git 76be507b2736:prebid_cache_client/client_test.go, and TestVTrackCacheKeyCannotAddPut in git 76be507b2736:endpoints/events/vtrack_test.go, which sends a vtrack key through the real client to a test server.
- Every producer of Cacheable.Data, which the encoder still writes as it is (git 76be507b2736:prebid_cache_client/client.go:189-190): the auction marshals each bid (git 76be507b2736:exchange/auction.go:247) and VAST (:268), and the debug log's CacheString (:86, :295), with jsonutil.Marshal, and modifyBidJSON adds wurl with jsonpatch.MergePatch (git 76be507b2736:exchange/events.go:94-98), so those are valid JSON. vtrack's put value is a json.RawMessage decoded from the request, but for a bidder allowed to modify VAST, ModifyVastXmlJSON decodes the JSON string (git 76be507b2736:endpoints/events/vtrack.go:322) and, when the decoded text holds </Impression>, returns the edited VAST as raw XML, json.RawMessage(vast), not a JSON string (:330); nothing re-encodes it before encodeValueToBuffer writes it. A bidder is allowed when it is enabled with modifyingVastXmlAllowed: true (59 bidder-info files at master) or is a name Prebid Server does not know, since vtrack.allow_unknown_bidder defaults to true (git 4e296450de2f:config/config.go:1130; vtrack.enabled defaults to true, :1131). The behavior dates from https://github.com/prebid/prebid-server/pull/1597 (2021-01-20); the 2020 version edited the JSON text in place. Run on master in a temporary worktree at 4e296450de2f (master's code only, not the PR's), a VAST holding </Impression> came back as <VAST version="3.0">… with json.Valid false. So, on master and with this PR, an edited VAST makes the PUT body invalid JSON, and the decoded value, which the /vtrack caller writes, can still change the PUT's structure, as key could before this PR; the new response-count check then reports extra entries after Prebid Cache has stored them. Issue 5075 names the /vtrack request body as a source. The PR's TestVTrackCacheKeyCannotAddPut passes an empty allowed-bidder map and Data true, so it does not reach this path. A /vtrack caller can already send any puts and keys, so the gain over that is small; the edited-VAST breakage is the larger effect. Raised for the author, as present before the PR.
- writeJSONString uses encoding/json's json.Marshal (git 76be507b2736:prebid_cache_client/client.go:217). Prebid Server's code outside the adapters marshals with jsonutil.Marshal (git 4e296450de2f:util/jsonutil/jsonutil.go:159) in 87 places at master, and calls encoding/json's json.Marshal once (git 4e296450de2f:floors/fetcher.go:166), after the change of JSON libraries (https://github.com/prebid/prebid-server/pull/3225). But core also writes responses with encoding/json's json.NewEncoder in 5 places (endpoints/openrtb2/auction.go:383, amp_auction.go:407, endpoints/cookie_sync.go:560, endpoints/getuids.go:26, exchange/exchange.go:984), and jsonutil, built on jsoniter's ConfigCompatibleWithStandardLibrary, escapes a lone string the same way. Consistency only; not raised.
- The description reports the one-put encoding going from about 75 to 137 ns (3 to 5 allocations) for a bid and 151 to 343 ns (5 to 13) for a vtrack put, about two allocations per string field. Small beside the HTTP call to Prebid Cache; not raised.
- The PR says it fixes https://github.com/prebid/prebid-server/issues/5075. Besides the vtrack value above, the issue's third point names /vtrack letting a client choose any cache key and TTL; vtrack passes the request's key and ttlseconds through (git 76be507b2736:endpoints/events/vtrack.go:243-244), as its API allows, and the PR leaves that. Whether the issue closes with this PR is the maintainers' call; not raised.

## For the author

- **VTrack value written unencoded**: For a bidder allowed to modify VAST (one with `modifyingVastXmlAllowed: true`, or any bidder name Prebid Server does not know, since `vtrack.allow_unknown_bidder` defaults to true), `ModifyVastXmlJSON` decodes the put's JSON string value (`endpoints/events/vtrack.go:322`) and, when it holds `</Impression>`, returns the edited VAST as raw XML rather than a JSON string (`vtrack.go:330`); `encodeValueToBuffer` then writes `value` as it is (`prebid_cache_client/client.go:189-190`). So an edited VAST makes the PUT body invalid JSON, and the decoded value can still change the PUT's structure, as `key` could before this PR. Issue 5075 names the /vtrack request body; `TestVTrackCacheKeyCannotAddPut` passes no bidder allowed to modify VAST, so it does not reach this path. Present before this PR.
